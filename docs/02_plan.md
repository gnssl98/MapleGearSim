## 1. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 계산 엔진 / 백엔드 | **Python 3.12 + FastAPI + NumPy** | 마르코프 체인, 몬테카를로, 확률 계산이 편함. 테스트(pytest)가 쉬움 |
| 프론트엔드 | **React + Vite + TypeScript**, 차트는 Recharts | 입력 폼과 결과 차트 UI. 빌드 결과물을 FastAPI가 정적 파일로 서빙 |
| 저장소 | CSV(시세), JSON(설정), YAML(게임 수치), 파일 캐시(API) | DB 없이 단순하게. 엑셀로 열람 가능 |
| 패키징 | `uv`(Python 의존성) + `start.bat` | Windows에서 원클릭 실행. 프론트는 미리 빌드해 둔 정적 파일을 포함 |

## 2. 단계별 계획

> 기간은 개인 프로젝트 기준의 대략적인 추정치(주말 위주)

### Phase 0 — 기반 구축 (0.5주)
- git 초기화, 프로젝트 골격, `start.bat`, 린트와 테스트 설정
- `data/game/` 스키마 정의(pydantic)와 리서치 수치 입력(스타포스, 잠재 등급업, 추옵)
- **산출물**: 빈 화면이 뜨는 로컬 앱, 수치 데이터 로딩 테스트

### Phase 1 — 직작 엔진: 스타포스 (1주) · **MVP**
- 비용 공식, 할인/이벤트 적용 규칙(MVP+PC방은 합산, 30% 할인은 곱연산, 파괴방지 추가 비용은 할인 제외)
- 마르코프 체인 기댓값(메소, 파괴 횟수), 몬테카를로 분포(NumPy 벡터화)
- 파괴 시 스페어 복구 비용 모델
- **검증**: 200제 12→18성 샤타포스 = 16.54억 / 파괴 0.42회 회귀 테스트, 외부 계산기 2곳 교차 검증

### Phase 2 — 직작 엔진: 잠재, 에디, 추옵 (1~1.5주) · **MVP**
- 등급업(확률 + 천장) 기댓값과 분포
- 옵션 확률표를 수집해 데이터화(공식 확률 페이지에서 부위 × 등급 × 레벨 단위로 수동 또는 반자동 수집 → JSON 저장)
- 목표 옵션 달성 확률 계산기(3줄 조합 열거), 프리셋
- 추옵 급수 확률 계산(티어 분포 조합), 급수 환산식 설정
- **검증**: 리서치의 수치(무기 공%·보공 3줄 0.418%, 상의 STR 33%+ 0.023%)와 일치

### Phase 3 — 직작 UI + 손익분기 + 시세 CSV (1.5주) · **MVP 완료**
- 직작 계산기 화면(단계별 탭, 결과 카드, 분포 히스토그램, 백분위 표)
- 손익분기 가격, 기대 이득/손해, 손해 확률
- 시세 매물 입력 폼, CSV 누적 저장, 목록과 필터, 타서버 실구매가 계산
- 설정 화면(MVP, PC방, 이벤트, 메소마켓 시세)
- **마일스톤 M1**: 요구사항 정의서 8장의 수용 기준 충족

### Phase 4 — 캐릭터 연동 (1주)
- 오픈 API 클라이언트(레이트 리미터, 캐시), ocid 조회, 장비와 스탯 로딩
- 잠재 옵션 텍스트 파서, 실제 응답으로 필드 검증(리서치 미검증 항목 해소)
- 내 장비 화면, 가상 장비 교체, 가위 횟수로 되팔기 판정

### Phase 5 — 환산(표 방식) + 업그레이드 추천 (1.5주)
- 환산표 기반 장비 기여도와 세트 효과 증감
- 후보 생성(매물 구매 / 추가 직작 / 베이스+직작), 억당 효율 랭킹, 구매와 직작 자동 비교
- 혼합 전략 비교, 이벤트 대기 비교
- 시세 추이 차트, 유사 매물 조회
- **마일스톤 M2**: "다음에 뭘 맞출지" 랭킹 사용 가능

### Phase 6 — 고도화 (이후)
- 데미지 공식 기반 환산(한계효용), 직업별 예외 처리
- 예산 최적 조합(부위별 다중 선택 배낭 문제 + 세트 효과는 탐색 또는 DP)
- 파괴방지 최적 전략 탐색, 보수적(백분위) 기준 추천
- 큐브(캐시/보스 재화) 경로 비교

## 3. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| 게임 패치로 확률이나 비용이 바뀜 | 계산 오류 | 수치를 데이터 파일로 분리하고 기준 패치 버전을 표기. 패치노트를 확인한 뒤 갱신 |

| 잠재 옵션 확률표 수집 범위가 넓음(부위 × 등급 × 레벨) | Phase 2 지연 | 자주 쓰는 부위와 레벨(200/250제)부터 수집하고 점진 확장 |
| 오픈 API 필드명과 포맷 불일치 | 파서 오류 | 실제 응답 샘플을 테스트 픽스처로 저장 |
| 환산이 외부 사이트와 다름 | 신뢰도 저하 | 계산 근거를 표시하고 계수 수정을 허용. 2단계에서 공식 방식 도입 |
| 시세 입력 부담 | 사용이 줄어듦 | 빠른 입력 폼(최근 입력 복제), 스펙 프리셋, 엑셀 편집 호환 |
